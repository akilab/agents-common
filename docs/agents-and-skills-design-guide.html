DESIGN BRIEF / REUSABLE WORKFLOWS

Agents / Skills を
依頼できる形にする

これは完成済みのテンプレート集ではなく、AIに「何を作ってほしいか」を正しく渡すための設計メモです。目的・境界・完成条件を先に言語化すると、後から手直ししやすい小さな部品になります。

01

最初に、置き場所を選ぶ

一度きりの依頼

まずは通常のプロンプトで十分です。繰り返し使うと分かってから、Skill や Agent に昇格させます。

繰り返す手順

Skill。同じ入力から、同じ判断手順・出力形式を再利用したいときに向きます。

独立した専門作業

Subagent。調査・レビュー・検証などを別コンテキストで走らせ、要約だけを戻したいときに向きます。

長く残すべき事実や規約は AGENTS.md / CLAUDE.md、機械的に必ず守らせる制約は Hooks や権限設定の担当です。

02

AIへ渡す、共通の設計ブリーフ

良い依頼は「何をするか」だけでなく、「何をしないか」と「いつ終わりか」を持ちます。 下の6項目を箇条書きで渡せば、AIは必要なファイル形式へ落とし込みやすくなります。

  • 1. 一つの目的誰が、どんな結果を必要とするのか。役割を一文で言えるようにする。
  • 2. 起動条件どんな依頼・状況で使うか。似ているが対象外のケースも書く。
  • 3. 入力前提にするファイル、引数、ユーザーから受け取る情報、不足時の扱い。
  • 4. 手順と道具必要な順番、使ってよいツール、読み取り専用か、外部操作の可否。
  • 5. 出力と完成条件返す形式、必須の根拠、検証方法、完了とみなす条件。
  • 6. 境界と停止条件推測してはいけないこと、変更してはいけない範囲、質問・停止すべき条件。
03

Skill を作るときに渡す情報

SKILL = REUSABLE WORKFLOW

設計上の要点

  • 一つの認識しやすいユーザー目的に絞る。
  • description に「何をするか」と「いつ使うか」を短く書く。
  • 本文には、入力 → 手順 → 出力 → 例外処理の順で命令を書く。
  • 詳細資料は references/、雛形は assets/、決定的な処理だけを scripts/ へ分ける。
ASK THE AI

依頼文の骨子

次の用途の Skill を設計してください。

目的: [利用者が達成したいこと]
起動条件: [使う依頼] / [使わない依頼]
入力: [必要な情報・ファイル]
手順: [守る順番・使う道具]
出力: [形式・必須項目]
境界: [推測禁止・外部操作の可否]
検証: [成功 / 失敗の確認方法]

最初にファイル構成と SKILL.md の概要を提案し、
不足する判断があれば質問してから作成してください。

「手順が何度も同じ」「長い手順書を毎回貼っている」が Skill 化の目安です。説明だけで十分なら、最初はスクリプトを追加しません。

04

Subagent を作るときに渡す情報

AGENT = SPECIALIST WORKER

設計上の要点

  • 担当範囲を狭くする。例: 「PRの根拠付きレビュー」「読み取り専用の調査」。
  • 主担当との受け渡しを決める。何を受け取り、どの粒度で要約して返すか。
  • ツールと権限を最小化する。調査役なら読み取り専用を基本にする。
  • 並列実行時に同じファイルを編集させない。書き込み役の所有範囲を分ける。
ASK THE AI

依頼文の骨子

次の用途のカスタム Subagent を設計してください。

担当: [専門役を一文で]
受け取る仕事: [入力・前提]
返すもの: [要約・ファイル参照・成果物]
許可する操作: [読み取り / 編集 / 実行]
禁止する操作: [変更範囲・外部操作]
完了条件: [いつ終了するか]
他の agent との関係: [依存・所有範囲]

まず片方の実装案を提案してから作成してください。

05

作成前の5問レビュー

本当に再利用するか？

一度きりなら通常のプロンプトへ戻す。設定ファイルは増やしすぎない。

一文で説明できるか？

目的や担当が一文で言えないなら、複数の Skill / Agent に分ける。

誤作動しても安全か？

広すぎる起動条件、過剰な権限、曖昧な外部操作は縮める。

結果を判定できるか？

出力形式・根拠・テストなど、成功を人間が判断できる形にする。

維持できるか？

変わりやすい詳細は参照ファイルへ。本文は短く、更新理由を残す。

誰の設定か？

個人で使うならホーム、チームで共有するならプロジェクト内に置く。
